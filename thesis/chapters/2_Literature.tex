\chapter{Literature Review}\label{chapter:literature}

The field of vehicle routing originated from the truck dispatching model of \citet{truck_dantzig_1959}. Subsequent research has treated the \gls{cvrp} as its canonical member, with a homogeneous fleet, capacity constraints, and one visit per customer \citep{tothVehicleRouting2014}. \citet{vidalConciseGuideExisting2020} and \citet{archetti2026beyond} review how that core model has been extended since.

This chapter states the \gls{cvrp} problem and the benchmark instances used in the computational study (Section~\ref{sec:lit-problem}). It then moves from the state-of-the-art solvers that (Section~\ref{sec:lit-large-cvrp}) to the techniques that scale and configure routing heuristics (Section~\ref{sec:lit-scalability}). Section~\ref{sec:lit-frameworks} covers the frameworks that wrap existing solvers, and Section~\ref{sec:lit-gap} outlines the remaining research gap.

\section{Problem Statement and Benchmark Instances}\label{sec:lit-problem}\label{chapter:problem}

The \gls{cvrp} is defined on a complete undirected graph $G = (V, E)$, where $V = \{0\} \cup C$ is the set of locations. Node $0$ represents the depot, and $C = \{1, \dots, n\}$ is the set of customers, so that $n = |C|$ is the customer count excluding the depot. Each edge $\{i, j\} \in E$ carries a non-negative travel cost $c_{ij} \geq 0$, and each customer $i \in C$ has a demand $q_i > 0$. A homogeneous fleet of vehicles with capacity $Q$ is dispatched from and returns to the depot. A solution is a set of routes that start and end at the depot, visit every customer exactly once, and respect the capacity $Q$ on every route. The objective is to minimize the total travel cost.

As a generalization of the \gls{tsp}, the \gls{cvrp} is NP-hard \citep{lenstraComplexityVehicleRouting1981}, and the number of feasible solutions grows factorially with $n$. This makes solving larger \gls{cvrp} instances with exact methods impractical. Nevertheless, branch-cut-and-price algorithms prove optimality for instances with a few hundred customers \citep{improved_pecin_2017,exact_costa_2019,generic_pessoa_2020}. But that still leaves them an order of magnitude short of the scale considered here. Heuristic and metaheuristic methods therefore trade the optimality guarantee for feasible solutions within a practical wall-clock time budget.

Existing heuristic research on the \gls{cvrp} has focused on a small number of benchmark sets. The X set of \citet{uchoaNewBenchmarkInstances2017} contains 100 instances with 100 to 1{,}000 customers, and is generated by varying four characteristic attributes across the set: depot position, customer distribution, demand distribution, and average route length. \citet{queirogaXLInstancesCapacitated2026} report that it became the primary benchmark for both exact and heuristic methods. It also formed the basis of the \gls{cvrp} track of the 12th DIMACS Implementation Challenge.\footnote{\url{http://wwwdimacs.dimacs.rutgers.edu/programs/challenge/vrp/}, accessed September 1, 2026.} \citet{queiroga2022optimal} also added the XML set of 10{,}000 instances with 100 customers each, providing optimal solutions for almost all of them. This allowed benchmarks of machine-learning heuristics to be evaluated against absolute error rather than a moving reference, as is the case for other instance sets.

Two additional collections reach far beyond 1{,}000 customers. The AGS set of \citet{efficiently_arnold_2019} contains ten instances with 3{,}000 to 30{,}000 customers, which were derived from parcel delivery in Belgium. The AV set of \citet{accorsiRoutingOneMillion2024} contains 20 instances with 20{,}000 to 1{,}000{,}000 customers, and were generated from sampled addresses in Italian regions. \citet{queirogaXLInstancesCapacitated2026} observe that all 30 of these instances draw their demands uniformly from one to three units, and that most of them have long routes. The existing sets also left a gap in the range from 1{,}001 to 2{,}999 customers.

The XL set of \citet{queirogaXLInstancesCapacitated2026} closes that range with 100 instances of 1{,}000 to 10{,}000 customers. They are generated very similarly to the X set, varying the same four attributes. \citet{queirogaXLInstancesCapacitated2026} released the set with initial \gls{bks} values from a selection of state-of-the-art solvers for large-scale instances. With their release, they opened the CVRPLib \gls{bks} Challenge,\footnote{\url{https://galgos.inf.puc-rio.br/cvrplib/index.php/en/bks_challenge/overview}, accessed September 1, 2026.} a community competition that started on January~12, 2026, with the goal to find new \gls{bks} values for the XL set without any further constraints. Chapter~\ref{chapter:study} uses this XL set and lists its attribute levels. Figures~\ref{fig:unsolved-instances} and~\ref{fig:solved-instances} in the appendix visualize two of these instances, unsolved and solved, for illustrative purposes.

\section{State-of-the-Art Solvers for Large-Scale CVRP}\label{sec:lit-large-cvrp}

On the XL set, the methods that produced the initial \gls{bks} values are metaheuristics that search over the complete solution space. This thesis uses the term monolithic for a method that maintains one complete feasible solution, or a population of them, under a single search process that can in principle modify any route. Neighborhoods may be localized or sparsified without affecting this classification. What falls outside it are independent customer partitions, solved separately and merged by an outer recombination layer.

\citet{queirogaXLInstancesCapacitated2026} ran AILS-II, FILO, FILO2, KGLS-XXL, HGS-CVRP, SISR, LKH-3, and OR-Tools on every XL instance, with 60 seeds of two hours per code on a single thread. Of the 100 initial \gls{bks} values, AILS-II found 93, FILO2 six, and FILO one. The authors report HGS-CVRP, SISR, LKH-3, and OR-Tools as an indication only, because their code implementations were not calibrated for instances with up to 10{,}000 customers. The two-hour time limit is the budget previously, that was also used on X instances of at most 1{,}000 customers.

A key concept that several of the above-mentioned solvers employ is \gls{ils}. \gls{ils} alternates a perturbation of the current solution with a local search that returns it to a local optimum. An acceptance criterion then decides which local optimum the next perturbation starts from \citep{lourencoIteratedLocalSearch2003}. \citet{lourencoIteratedLocalSearch2003} argue that the perturbation strength governs the behavior of the method. A perturbation that is too weak lets the local search fall back into the same local optimum, while one that is too strong turns the method into a random restart. The classical example calibrated to that tension is the double-bridge move of \citet{martinLargestepMarkovChains1991}, which a simple local search built from small moves cannot undo in one step.

AILS-II, developed by \citet{maximoAILSIIAdaptiveIterated2024}, utilizes an adaptive \gls{ils} for large-scale \gls{cvrp} instances. It extends a predecessor, AILS-PR \citep{maximoHybridAdaptiveIterated2021}, which hybridizes adaptive \gls{ils} with path relinking and performs well up to 1{,}000 customers. AILS-II adapts the perturbation degree during the search, and later during convergence, it draws the solution to be perturbed from an elite set. Its original experiments reach 30{,}000 customers on the AGS set, where it reported lower average gaps than both AILS-PR and HGS on all ten instances.

\citet{accorsiFastScalableHeuristic2021} build FILO as an \gls{ils} with a simulated-annealing acceptance criterion \citep{optimization_kirkpatrick_1987}. Granular neighborhoods \citep{tothGranularTabuSearch2003} restrict move evaluation to a subset of promising arcs, and selective vertex caching restricts it further to recently changed vertices. FILO2 \citep{accorsiRoutingOneMillion2024} carries this design to instances with up to one million customers, with pointed changes to improve scalability. But solvers still localize the search inside one full solution, rather than partitioning the customer set into independently solved subproblems.

Hybrid genetic search evolves a population of complete solutions and improves offspring by local search \citep{vidalHybridGeneticAlgorithm2012}. \citet{vidalHybridGeneticSearchCVRP2022} published HGS-CVRP as an open implementation for the \gls{cvrp} with the SWAP* neighborhood, and \citet{woudaPyVRPHighPerformanceVRP2024} provide PyVRP, a separate implementation of the same paradigm. The comparison of \citet{queirogaXLInstancesCapacitated2026} uses the HGS-CVRP code.

Those same experiments show that the leading method changes with scale. On the XML instances and on the smaller half of the X set, up to about 330 customers, HGS-CVRP has the best average solution quality of the eight codes, while AILS-II leads on the larger half of the X and dominates on XL. \citet{queirogaXLInstancesCapacitated2026} interpreted this as a transition from population-based search, which evolves several complete solutions at once, to single-trajectory search.

The remaining state-of-the-art solvers follow different designs. The knowledge-guided local search of \citet{knowledgeguided_arnold_2019} applies CROSS-exchange, relocation chains, and Lin-Kernighan moves to a complete solution. When a local optimum is reached, it penalizes long and wide edges so that later moves leave those edges out. \citet{efficiently_arnold_2019} scale that design to instances with up to 30{,}000 customers as KGLS-XXL by pruning neighborhoods and storing only nearest-neighbor distances. SISR \citep{christiaensSlackInductionString2020} ruins a solution by removing geographically adjacent strings of customers. That removal concentrates unused capacity on a few nearby routes. It then reinserts the customers by greedy insertion with blinks, skipping some candidate positions at random. A simulated-annealing criterion accepts or rejects the rebuilt solution. LKH-3 transforms constrained routing problems into a \gls{tsp} with penalties, then applies the Lin-Kernighan-Helsgaun local search to the result \citep{helsgaunExtensionLinKernighan2017}. An earlier variable neighborhood search had already addressed instances with up to 20{,}000 customers \citep{kytojokiEfficientVariableNeighborhood2007}.

POPMUSIC \citep{queirogaPOPMUSICMatheuristic2021} is the exception among the competitive large-scale methods. It reoptimizes subproblems extracted from a complete solution, and is therefore not a monolithic solver. Section~\ref{sec:lit-decomposition} discusses it with the other decomposition methods.

\section{Scaling and Configuring Routing Heuristics}\label{sec:lit-scalability}

Exact methods fail at scale because the solution space grows factorially, but local-search heuristics face a different cost. What grows with $n$ is the effort of neighborhood evaluation, the memory for move descriptors and caches, and the number of iterations needed to reach a given quality \citep{efficiently_arnold_2019,accorsiFastScalableHeuristic2021}.

Literature offers several ideas to tackle the scalability problem. Parallel search spreads the effort over processors (Section~\ref{sec:lit-parallelization}), and route pools recombine routes found earlier by set covering or set partitioning (Section~\ref{sec:lit-set-covering}). Decomposition splits the customer set into smaller subproblems (Section~\ref{sec:lit-decomposition}), which leaves seams that later steps must repair (Section~\ref{sec:lit-boundary-repair}). Adaptive control and learned policies then decide which operator, configuration, or partition to apply (Sections~\ref{sec:lit-adaptive-control} and~\ref{sec:lit-learned-decomposition}).

\subsection{Parallel Search}\label{sec:lit-parallelization}

\citet{crainicParallelSolutionMethods2008} and \citet{crainic2019parallel} classify parallel metaheuristics by how they split the search. Low-level parallelism accelerates neighborhood evaluation inside one trajectory. Multi-search strategies run several trajectories, either independently or as cooperating searches that exchange knowledge such as complete solutions. \citet{crainic2019parallel} concentrates on cooperative strategies, and describes those built on asynchronous exchanges as the most effective of them.

Applied to vehicle routing, these designs multiply processor effort on the full instance. \citet{groerParallelAlgorithmVehicle2011} combine heuristic local search with integer programming across as many as 129 processors. \citet{jinCooperativeParallelMetaheuristic2014} run cooperative tabu-search threads that share a common solution pool, where entering solutions are clustered by similarity so that the clusters can balance between intensification and diversification more effectively.

In both methods, every worker still searches the full customer set. Parallelism changes how many neighborhoods or incumbents are examined per wall-clock second, without reducing the size of the problem each worker faces. \citet{parallel_taillard_1993} instead partitions the customers geographically and solves the resulting subproblems with parallel iterative search. But solving customer subsets concurrently requires a dedicated decomposition layer, discussed later in Section~\ref{sec:lit-decomposition}.

\subsection{Route Pools and Set Partitioning}\label{sec:lit-set-covering}

Using set covering or set partitioning over routes has been an approach that is older than local search metaheuristics. \citet{balinskiIntegerProgramDelivery1964} formulate delivery as an integer program over routes, and \citet{garfinkelSetPartitioningProblemSetCovering1969} treat set partitioning as set covering with equality constraints. \citet{foster1976integer} solve the set partitioning model of vehicle scheduling with the revised simplex method, restricting the columns to routes through radially contiguous locations. Their test problems range from 21 to 100 locations. Once a collection of feasible routes exists, selecting a subset that covers each customer once is an integer program whose size tracks the number of routes rather than $n$.

In more modern approaches, \citet{rochatProbabilisticDiversificationIntensification1995} store elite routes in an adaptive memory, draw new starting solutions from it probabilistically, and recombine the stored routes by set covering. The local search generating the routes and the model recombining them are already separate components here. \citet{taillard2001adaptive} describe this scheme as adaptive memory programming and argue that several metaheuristics share it. The memory of solution components builds new starting solutions, a local search improves them, and the results update the memory. \citet{kelly1999set} combine route generation by heuristics with a set partitioning model that selects among the generated routes.

\citet{hybridizing_jourdan_2009} classify such combinations of exact methods and metaheuristics in a taxonomy of hybrid approaches. Several \gls{cvrp} heuristics apply the pattern repeatedly during the search rather than once at the end. \citet{hybrid_subramanian_2013} hybridize \gls{ils} with a set partitioning model over the routes it generates. \citet{cavaliereIntegratedLocalsearchSetpartitioning2022} alternate LKH-3 local search with a restricted set partitioning program. It was allowed to run 24 hours past its last improvement, and reported new best known solutions for large-scale \gls{cvrp} instances. FSP4D, a finalist of the 12th DIMACS Implementation Challenge, follows the same alternation with a FILO-based fast \gls{ils} feeding a route pool and then running a set partitioning heuristic to identify high-quality combinations \citep{accorsiIterativeFastOptimization2022}.

\citet{arenasvasco2025meta} quantify the benefit of this route and set partitioning pattern. Their analysis covers 30 set partitioning or set covering matheuristics for vehicle routing problems, selected from 54 eligible studies. The recombination step improved solution quality by 0.51\% on average, with a 95\% confidence interval of 0.41 to 0.61\%. The authors describe the gain as modest but consistent across implementations.

A central problem of recombination is that set covering or set partitioning can only choose among routes that some other component has already generated. But this also means a pool dominated by the routes of one incumbent reproduces that incumbent, effectively rendering the set partitioning pointless. The diversity of the result is bounded by the diversity of whatever feeds the pool new routes. The recombination step itself decides nothing about how the instance is split, which solver generates the routes, or how either choice changes during a run.

\subsection{Decomposition}\label{sec:lit-decomposition}

A decomposition method splits the instance into smaller subproblems, solves each one, and then reassembles a complete solution. How good this divide-and-conquer solution is depends on where the cuts fall, how often they are redrawn, and how the pieces are joined back together. Two central questions in decomposition literature are whether the customers are grouped before or after a tour is built, and whether the groups are formed from customer coordinates or from the routes of an incumbent solution.

The Cluster-first route-second approach answers the first question by partitioning the customers and then routing each cluster. There are various clustering methods following that approach. The sweep algorithm of \citet{gillettHeuristicAlgorithmVehicleDispatch1974} forms clusters by polar angle around the depot and solves a \gls{tsp} on each. \citet{fisherGeneralizedAssignmentHeuristic1981} assign customers to vehicle seeds through a generalized assignment problem before routing each assignment. \citet{kerscherDecomposerouteimproveFrameworkSolving2025} and \citet{karaahmetogluAdaptiveClusterFirst2026} follow the same order with modern components, building a customer partition and routing its clusters with existing solvers.

Route-first cluster-second reverses that order. \citet{beasley1983route} constructs a single tour through all customers, then partitions it into capacity-feasible routes, optimally for the given order. \citet{simple_prins_2004} embeds this split procedure in a genetic algorithm that encodes solutions as giant tours. The clustering step then operates on a customer sequence rather than on an unstructured point set.

The second question only arises once a partition budget is fixed, and it separates vertex-based from route-based clustering. Vertex-based clustering partitions the customer set directly, which is what the clustering step of cluster-first route-second does. Route-based clustering instead requires a complete incumbent, grouping customers that already share a route or clustering the routes themselves by their barycenters.

\citet{bent2010spatial} study adaptive schemes that repeatedly decompose a \gls{vrptw} instance from the current solution. In their reading, vehicle-based decompositions, which partition the vehicles of the incumbent across subproblems, cannot express temporal splits and may produce spatial splits that are not focused enough. They propose customer-based decompositions instead. On class R2 of the extended Solomon benchmarks, the customer-based variants improved on plain large neighborhood search where the vehicle-based ones did not.

\citet{santiniDecompositionStrategiesVehicle2023} compare decomposition strategies inside \gls{alns} \citep{pisingerGeneralHeuristicVehicle2007} and hybrid genetic search \citep{vidalHybridGeneticAlgorithm2012} on the X instances. Route-based decompositions, which group customers that already share a route, outperformed path-based coarsening, which merges customers into supernodes. Barycenter clustering was the strongest strategy of those tested, improving both host algorithms relative to runs without decomposition. The benefit depended on the strategy and on the instance, and a poor decomposition failed to help at all. Subproblem size and decomposition frequency both required calibration. Their \gls{alns} learns destroy and repair weights within the run, but the decomposition method itself stays a fixed, calibrated choice.

The two studies favor different paradigms. \citet{bent2010spatial} find customer-based decompositions stronger on a class of \gls{vrptw} instances, while \citet{santiniDecompositionStrategiesVehicle2023} obtain their best results with a route-based strategy on the \gls{cvrp}\@. Because the studies differ in problem, host heuristic, and benchmark, the comparison does not isolate the cause.

Another decomposition approach, POPMUSIC \citep{taillard2002popmusic}, starts from a complete solution and optimizes sub-parts of it until a local optimum is reached. \citet{queirogaPOPMUSICMatheuristic2021} apply the idea to the \gls{cvrp}, using a branch-cut-and-price algorithm as a heuristic on subproblems of typically 25 to 200 customers. The main experiments cover instances of 302 to 1{,}000 customers. Long runs started from strong incumbents or CVRPLib \gls{bks} values improved several best known solutions, including some on very large instances. The method needs a complete solution before it can cut, and it uses a fixed subproblem policy. Its exact subsolver is also not an interchangeable off-the-shelf heuristic in the sense of Section~\ref{sec:lit-frameworks}.

\subsection{Repairing Decomposition Boundaries}\label{sec:lit-boundary-repair}

Each subproblem of a decomposition can be solved well in isolation while the assembled solution still carries defects along the cuts. A partition drawn from coordinates or route centroids uses no information about which customers a vehicle will end up serving together. Routes on either side of a cut may therefore be cheaper when reconnected across it. Decomposition and recombination therefore introduce a structural suboptimality of their own. The literature suggests four approaches on how to deal with the seams in between two clusters.

The first is to redraw the cut. Iterative schemes decompose again from the current solution at regular intervals \citep{bent2010spatial,santiniDecompositionStrategiesVehicle2023}, so that a seam of one iteration can fall inside a subproblem of a later one. Whether any given seam is repaired then depends on where the next partition happens to cut.

The second is to take the subproblems from the incumbent in the first place. POPMUSIC follows this pattern \citep{taillard2002popmusic,queirogaPOPMUSICMatheuristic2021}. Because every subproblem is carved out of the current solution, the method does not introduce the structural suboptimalities in the first place, which would need to be repaired.

The third is an explicit improvement step after the subproblem solutions are concatenated. \citet{kerscherDecomposerouteimproveFrameworkSolving2025} apply local search to inter-route moves between subproblems, and prune it with relational data from the clustering step. A move is evaluated only when the two subproblems lie within a vicinity of each other in a dissimilarity matrix already used for the decomposition. Where fuzzy clustering was used, a customer additionally qualifies only when its highest membership degree falls below a certain threshold, which marks it as boundary-adjacent. The pruning therefore concentrates the improvement budget on the customers the decomposition placed at a seam.

The fourth is recombination through a set covering step \citep{kerscherSolvingHeterogeneousVehicle}. They select routes from a pool holding the output of many decompositions. A route that one partition cut badly can then be replaced by a route from another, more favorable partition.

In all four, the partition information decides where the next subproblem falls or which moves the local search evaluates. We found no method in the reviewed literature that uses the partition boundaries to place a perturbation before a local search starts.

\subsection{Adaptive Operator Selection and Algorithm Configuration}\label{sec:lit-adaptive-control}

Every heuristic in this review exposes a number of parameters, and many offer alternative operators. \citet{eibenParameterControlEvolutionary1999} distinguish parameter tuning, which fixes values before a run, from parameter control, which changes them during one. Offline configurators like the irace package of \citet{lopezibanez2016irace} automate the tuning side by racing candidate configurations on a set of training instances and eliminating those that a statistical test finds worse. The result is one configuration for the instance class that the training set represents.

Automated algorithm selection asks the same question at the level of whole algorithms. \citet{kerschke2019automated} observe that for practically every intensely studied computational problem, different instances are best solved by different algorithms. Per-instance selectors exploit this complementarity by predicting from instance features which algorithm of a portfolio to run. The scale transition that \citet{queirogaXLInstancesCapacitated2026} observe on the \gls{cvrp} is one instance of such complementarity. But both tuning and per-instance selection are trained before the test instance is solved.

Online operator selection adapts during the run instead. The \gls{alns} of \citet{ropkeAdaptiveLargeNeighborhood2006} updates roulette-wheel weights of destroy and repair heuristics from scores collected during the search, and \citet{pisingerGeneralHeuristicVehicle2007} apply the same adaptive layer across five vehicle routing variants. \citet{mara2022survey} survey 252 publications on \gls{alns} from 2006 to 2021, and \citet{voigt2025review} reviews and ranks the operators used in \gls{alns} for vehicle routing problems.

The selection problem can be read as a multi-armed bandit. The search observes the reward of the operator it applied, but not what the other operators would have produced \citep{auerFinitetimeAnalysisMultiarmed2002}. \citet{fialhoAnalyzingBanditbasedAdaptive2010} analyze bandit-based adaptive operator selection mechanisms in this setting. Surveys of hyper-heuristics \citep{burkeHyperheuristicsSurvey2013} and of machine learning in metaheuristics \citep{karimiMamaghanMachineLearning2022} place the work in a broader literature on choosing heuristics during a search.

The evidence on what adaptive selection buys is mixed. \citet{turkes2021meta} run a meta-analysis of 25 \gls{alns} implementations against their non-adaptive variants. On average, the adaptive layer improved the objective function value by 0.14\%, with a 95\% confidence interval of 0.06 to 0.21\%. Its value depends on the set of heuristics it selects from, and because the layer adds complexity, the authors recommend it only in specific situations.

Reinforcement learning replaces the roulette update with a trained policy. \citet{kallestad2023general} train a deep reinforcement learning agent that selects the next low-level heuristic from features of the search state. It outperformed \gls{alns} and uniform random selection on four combinatorial optimization problems. But unlike \gls{alns}, it was not hurt by a larger set of heuristics. \citet{reijnen2024online} use deep reinforcement learning for the online control and configuration of \gls{alns}\@. Both policies are trained on sets of instances before they are applied.

What this literature adapts are operators inside one search process. In the work reviewed here, neither the decomposition of the instance nor the choice of subsolver is among them. Online control also moves part of the design problem into the update rule. The adaptive layer of \gls{alns} carries its own parameters, among them a reaction factor, a segment length, and the score values \citep{ropkeAdaptiveLargeNeighborhood2006}.

\subsection{Learned Decomposition}\label{sec:lit-learned-decomposition}

Machine learning for combinatorial optimization has grown into a research line of its own \citep{bengio2021machine}. For routing, \citet{kool2019attention} train attention-based construction policies with reinforcement learning on instances of up to 100 customers. \citet{queirogaXLInstancesCapacitated2026} observe that machine-learning methods for the \gls{cvrp} were rarely tested on standard benchmark sets, and often relied on ad hoc instance generators instead.

Learning-based work on large instances has turned to decomposition. \citet{liLearningDelegate2021} train a Transformer to choose which spatially local subproblem to delegate to a black-box subsolver, applying the policy iteratively on instances of roughly 500 to 3{,}000 customers. \citet{houGeneralizeLearnedHeuristics2023} train a two-stage divide method that partitions a \gls{cvrp} instance into traveling salesman subproblems, and report real-time solutions beyond 5{,}000 nodes. \citet{yeGLOP2024} combine a learned global partition policy with local construction in GLOP\@.

These policies are trained before the test instance is solved. They can be applied iteratively at test time, but the mapping from instance features to a partition or a delegation is not updated from the costs observed on that instance.

\citet{karaahmetogluAdaptiveClusterFirst2026} use a pretrained large language model in place of a trained policy. The model selects clustering, balancing, and refinement actions over a hierarchical cluster tree from partition diagnostics alone, without feedback from solution costs. The method builds one partition per run, then routes the clusters with the guided local search of OR-Tools. But it addresses the \gls{hvrp}, and the preprint reports no gaps on either the X or the XL set for \gls{cvrp}.

\section{Algorithmic Frameworks}\label{sec:lit-frameworks}

\citet{sorensenMetaheuristicsMetaphorExposed2015} distinguishes a metaheuristic as a problem-independent framework from a problem-specific implementation of its guidelines, and \citet{sorensenHistoryMetaheuristics2018} keep that vocabulary. This thesis uses three terms. A framework is a reusable control structure that can wrap existing solvers. A solver is a concrete implementation that searches a routing instance, such as AILS-II, FILO, FILO2, or PyVRP\@. A heuristic is any procedure that returns a feasible solution without an optimality guarantee. Every solver named above is a heuristic, though not every heuristic is a framework.

A framework for the \gls{vrptw} is proposed by \citet{kerscherDecomposerouteimproveFrameworkSolving2025}. Their \gls{dri} framework is built on three phases. The decomposition phase clusters customers under a spatial-temporal-demand dissimilarity, which scales the pairwise spatial distance by the scheduling flexibility and the capacity consumption of the customer pair. The partition therefore reflects the objective and the constraints rather than geography alone. The routing phase solves each resulting sub-VRPTW independently with an existing solver, PyVRP in their experiments. The improvement phase then applies the pruned local search of Section~\ref{sec:lit-boundary-repair} to the concatenated result.

Two properties of the \gls{dri} matter for the comparison drawn in Section~\ref{sec:lit-gap}. First, the number of subproblems is not a handcrafted constant. \citet{kerscherDecomposerouteimproveFrameworkSolving2025} evaluate the silhouette coefficient of the clustering over a range of candidate counts and take the maximizing value, so that the granularity of the partition adapts to each instance. They report that this matches a perfect-information baseline closely on clustered instances, at a fraction of its runtime. Second, that criterion measures cluster compactness and separation rather than routing cost, and it is evaluated once before the routing phase begins. The clustering algorithm, the dissimilarity metric, the vicinity size, and the fuzzy threshold are all compared offline in a sensitivity analysis and then held fixed. Their computational study covers the Gehring and Homberger instances together with a new set of 20 very large-scale VRPTW instances of 3{,}000 to 30{,}000 customers. On that new set, the \gls{dri} reports lower costs than PyVRP on every instance where PyVRP found a usable solution. PyVRP failed to produce one on most instances with tight time windows.

\citet{kerscherSolvingHeterogeneousVehicle} extend the pattern to the \gls{hvrp} in DRSCI, whose four steps give it its name. Each iteration decomposes the instance with $k$-means clustering, either over customer vertices or over the routes of the current best solution. Each cluster becomes a sub-instance by duplicating the depot and assigning a sub-fleet to it. The routing step then generates routes for each sub-instance through one of four strategies. These solve it as several independent homogeneous VRPs, as connected prize-collecting VRPs, through a giant-tour partitioning procedure, or directly with an \gls{hvrp} solver. All generated routes enter a route pool, and a set covering model selects a subset from it. A savings-based heuristic then removes the customers that appear in more than one selected route, before local search refines the result.

How DRSCI chooses its configuration is the part closest to this thesis, so it is worth stating precisely. The clustering paradigm is a coin flip in every iteration, with vertex-based and route-based clustering equally likely. The number of clusters and the routing strategy follow a scheme that their hyperparameter tuning selected over a fully random alternative. Under that scheme, every routing strategy is applied exactly once at the current cluster count before the count advances. The candidate counts are drawn from powers of two bounded by the route count of a feasible solution. Once a solution exists, the candidate range narrows to the interval spanned by the smallest and the largest cluster count that contributed a route to the current best solution. DRSCI therefore does use within-run feedback on one dimension of its configuration, by restricting a range rather than by weighting options. Their study covers heterogeneous-fleet instances of 101 to 1{,}001 vertices. DRSCI improved the previous best known solution on 14 of the 60 FSMVRP instances in the XH dataset, and on 561 of the 600 FSMVRPTW instances. The published experiments run single-threaded, though the authors note that route generation is parallelizable by design.

An unpublished project study adapted DRSCI to the \gls{cvrp} and reported a mean gap of 0.53\% to the initial XL \gls{bks} values \citep{altendeiteringDRSCICVRP2026}. That study drew its decomposition and routing configuration uniformly at random in every iteration.

\section{Research Gap}\label{sec:lit-gap}

No published decomposition framework maintains weights over its decomposition and subsolver choices and updates them from the solution costs observed on the instance it is solving. The reviewed methods settle that configuration in one of five ways:
\begin{itemize}
  \item By a fixed rule or a calibrated default \citep{parallel_taillard_1993,queirogaPOPMUSICMatheuristic2021,santiniDecompositionStrategiesVehicle2023},
  \item By a clustering-quality criterion evaluated once per instance, before routing begins \citep{kerscherDecomposerouteimproveFrameworkSolving2025},
  \item By a schedule that cycles the routing strategies and narrows the cluster-count range to the interval spanned by the counts that contributed routes to the incumbent \citep{kerscherSolvingHeterogeneousVehicle},
  \item By a policy trained before the test instance is solved \citep{liLearningDelegate2021,houGeneralizeLearnedHeuristics2023,yeGLOP2024}, or
  \item By a pretrained model that reads partition diagnostics without cost feedback \citep{karaahmetogluAdaptiveClusterFirst2026}.
\end{itemize}

DRSCI \citep{kerscherSolvingHeterogeneousVehicle} is the closest of these to this thesis. Its narrowing rule does react to the instance at hand, but it acts on the cluster count alone. It selects uniformly inside the narrowed range, and it credits neither the clustering paradigm nor the routing strategy with the quality of what they produced. The \gls{dri} \citep{kerscherDecomposerouteimproveFrameworkSolving2025} adapts its granularity per instance as well, from a criterion that never observes a routing cost.

The evidence on whether closing that distance pays off points in two directions. \citet{turkes2021meta} find a small average benefit from the adaptive layer in \gls{alns}, whereas trained controllers outperformed roulette-wheel selection on the problems where they were tested \citep{kallestad2023general}. Neither body of work adapts a decomposition or a subsolver, so whether online control helps at that level has not been tested.

Algorithm-agnostic solver plug-in, parallel subproblem solving, route-pool recombination by set covering or set partitioning, and evaluation on the XL set all fall within the scope of this thesis. Taken separately, none of them is the gap. Table~\ref{tab:lit-research-gap} records which published methods combine which of them.

Table~\ref{tab:lit-research-gap} can be read in two directions. Down the four capability columns, the entries fill in over time. Decomposition, route-pool recombination, and an algorithm-agnostic solver interface grew as separate lines of work, and \citet{kerscherSolvingHeterogeneousVehicle} is the first published row to combine all three. Down the Configuration column, no such progression appears. Every row above the last fixes its configuration before the instance is seen, or derives it from a rule that never observes a routing cost. The gap is therefore not a capability that the literature lacks. It is a control layer over capabilities that already coexist.

Chapter~\ref{chapter:framework} introduces \gls{drispi} against that reading. It keeps the decompose-route-improve \gls{dri} loop and the persistent route pool of the frameworks in Section~\ref{sec:lit-frameworks}. What it replaces is their configuration layer. A controller draws the decomposition and the subsolver from weighted alternatives in every iteration, and updates those weights from a reward scored on each iteration's outcome. Two further elements answer points raised earlier in this chapter. The improvement stage places its perturbation on the subcluster boundaries, which Section~\ref{sec:lit-boundary-repair} found missing from the reviewed repair strategies. Finally \gls{drispi} is a highly parallelized framework, which both frameworks in Section~\ref{sec:lit-frameworks} note as possible extension but left unimplemented.
